# Bug Description

The affected Zephyr queue implementation has a lost-wakeup race in its `CONFIG_POLL` path. `k_queue_poll` calls `k_poll` to wait for data. A producer can satisfy the poll event, causing `k_poll` to report success, while another consumer removes the queued node before the waiting thread performs its locked queue recheck.

The recheck then finds `data_q.head == NULL`. Instead of returning to the wait loop for a `K_FOREVER` request, the vulnerable path passes the empty node through `z_queue_node_peek` and returns NULL. This violates the allocator's assumption that an infinite wait cannot fail.

Bluetooth initialization reaches this path through `bt_hci_cmd_create` and `net_buf_alloc_fixed(&hci_cmd_pool, K_FOREVER)`. `bt_hci_cmd_create` checks the returned buffer only with `__ASSERT_NO_MSG`, which is absent from the release binary, and then calls `net_buf_reserve`. That routine computes the embedded buffer member from a NULL base and writes through the resulting low address. The queue wait must retry after a successful poll followed by an empty recheck, and the caller must still handle NULL in non-assert code.
