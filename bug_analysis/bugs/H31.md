# Bug Description

`bt_spi_send()` handles a nonzero `bt_spi_transceive()` result by entering its
common cleanup path and calling `net_buf_unref()` on the outgoing buffer before
returning the error. This violates the Bluetooth HCI send contract: when a lower
driver reports failure, ownership remains with the caller so that the caller can
clean up its own reference.

The HCI transmit path retains a command reference before calling the driver. On
an SPI error, the driver's premature unreference is followed by the caller's
normal error cleanup of the same buffer. The resulting double release can
corrupt the network-buffer reference state, causing a denial of service and
potentially further memory corruption. The associated vulnerability identifier
is **CVE-2022-3806**. The
[Zephyr security advisory](https://github.com/zephyrproject-rtos/zephyr/security/advisories/GHSA-w525-fm68-ppq3)
independently corroborates this ownership error and network-buffer double free.

The trigger is hardware-feasible on this target. The STM32F429ZI build uses the
X-NUCLEO-IDB05A1 shield, whose SPBTLE-RF network processor communicates with the
host through SPI and GPIOs ([ST UM1912 Rev 1, sections 2.2 and 3.1](https://www.st.com/resource/en/user_manual/dm00210197-getting-started-with-x-nucleo-idb05a1-ble-expansion-board-based-on-the-spbtle-rf-module-for-stm32-nucleo-stmicroelectronics.pdf)).
The STM32 SPI driver can return `-EIO` for hardware error flags documented by
[ST RM0090, SPI error flags](https://www.st.com/resource/en/reference_manual/dm00031020.pdf),
so the failing-transfer condition does not depend on a reserved or
hardware-impossible peripheral state.
