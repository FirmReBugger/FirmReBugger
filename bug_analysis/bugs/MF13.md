# Bug Description

`cmd_send` accepts a device-name argument and resolves it through the subsystem-neutral `device_get_binding`. Because the registry contains every configured device class, an attacker can select a valid non-CAN object.

The handler passes that object directly to `can_send`. Its inline wrapper interprets the object's API table as `can_driver_api`, loads the CAN send slot, and invokes it with a CAN frame, timeout, and completion callback. On another device class, that offset can hold an unrelated function with an incompatible signature or an invalid pointer.

The command must validate the device API type before CAN dispatch and reject registered devices from other subsystems.
