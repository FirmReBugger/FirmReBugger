# Bug Description

This is [CVE-2020-14935](https://nvd.nist.gov/vuln/detail/CVE-2020-14935).
Contiki-NG's
[`snmp_engine_get_bulk`](https://github.com/contiki-ng/contiki-ng/blob/release/v4.4/os/net/app-layer/snmp/snmp-engine.c#L116-L130)
saves the incoming varbind count and then copies each requested OID into
`oid[SNMP_MAX_NR_VALUES][SNMP_MSG_OID_MAX_LEN]`. In this build,
`SNMP_MAX_NR_VALUES` is two, but the copy loop uses the unchecked incoming
count as its bound.

The preceding message decoder likewise loops while packet bytes remain rather
than stopping at `SNMP_MAX_NR_VALUES`, records the resulting count, and passes
it directly to the bulk handler. When a bulk request supplies a third varbind,
the handler forms `oid[2]` and passes it to `snmp_oid_copy`. This destination
is immediately beyond the two-row stack array, so the copied OID components
overwrite adjacent stack state. Further varbinds advance the destination by
another sixteen words and can eventually corrupt saved control data.

A correct fix rejects a decoded varbind count greater than
`SNMP_MAX_NR_VALUES` before the fixed varbind and OID arrays are indexed. The
bulk handler should retain its own capacity check rather than relying only on
an upstream parser.
