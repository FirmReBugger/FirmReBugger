# Bug Description

`st_cycle_reinitialize` checks whether the global `current_block` pointer is
NULL on entry, then falls through a few instructions later and re-loads the
same pointer to hand it to `plan_cycle_reinitialize`, with interrupts left
enabled across that gap. The stepper subsystem's periodic timer interrupt
independently clears `current_block` back to NULL whenever it finishes
stepping a block, so if that interrupt lands in the narrow window between
the check and the later use, the function ends up dereferencing NULL.

# False Positive Reason

The stepper timer is explicitly disabled — both its counter and its own
interrupt-enable bits — whenever the machine isn't actively stepping, and is
only re-armed once a new motion segment actually starts. `st_cycle_reinitialize`
runs on a cycle-start/resume request, which is exactly the kind of moment
where the timer is normally idle rather than mid-step. Reaching this crash
therefore depends on the stepper timer's interrupt firing while the timer
itself is disabled — something real hardware cannot do, since a disabled
timer cannot signal the interrupt controller at all. This is consistent with
the execution environment injecting peripheral interrupts on a fixed schedule
independent of whether the emulated peripheral's own enable state would
allow that interrupt on real hardware.
