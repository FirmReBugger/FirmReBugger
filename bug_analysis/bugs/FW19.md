# Bug Description

`HAL_I2C_Mem_Read` receives into a caller-provided buffer and stores that address in the global `hi2c1.pBuffPtr` field. Because the API is blocking, the caller's small stack buffer ceases to exist when the read wrapper returns, but the handle still retains the old address.

`I2C_ITError` assumes `pBuffPtr` belongs to an active asynchronous transfer. Its recovery path writes a peripheral byte through that pointer and advances it. If an error interrupt enters after the blocking call has returned, the store lands in whichever later stack frame reused the same address. A single byte can corrupt a pointer or saved value, and later derived stores can amplify the damage.

# False Positive Reason

The STM32F103RB requires `I2C_CR2.ITERREN` for error-interrupt delivery. The blocking memory-read path polls status and never enables the I2C event, buffer, or error interrupt bits. The separate asynchronous transmit path clears those bits before releasing the shared bus. Thus the retained pointer exists, but the physical peripheral cannot invoke the error handler during its stale lifetime. The enable contract is documented in [RM0008](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).
