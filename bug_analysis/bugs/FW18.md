# Bug Description

`planner_recalculate_trapezoids` walks the planner's ring buffer of queued
motion blocks backwards, recomputing acceleration/deceleration parameters
for each pair of adjacent blocks. On each iteration it tracks both the block
it's currently examining and the block that follows it, and once the loop
reaches the oldest queued block it falls through to a final step that
reuses whichever "next block" pointer the loop last computed, to finish the
calculation for that last block.

That final step never checks that the loop actually ran at least once. When
the planner buffer holds exactly one block — which is exactly the case the
very first time a motion command is queued after the buffer starts out
empty — the loop's exit condition is already true before its body ever
executes, so the "next block" pointer is never assigned and keeps its
initial value of NULL. The final step then dereferences that NULL pointer.

Because this path runs on every call to `planner_recalculate_trapezoids`
whenever the buffer transitions from empty to holding its first block, it
triggers on the first ordinary G-code motion command (for example, a plain
`X0` move) sent to a freshly reset controller — no unusual input is needed.
