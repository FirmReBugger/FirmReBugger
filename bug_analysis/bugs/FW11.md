# Bug Description

`settings_store_global_setting` handles one of the numeric `$<n>=<value>`
configuration commands by taking the parsed floating-point value, rounding
it, converting it to an integer, and truncating it to a single byte before
storing it in a global settings field — with no check that the resulting
value falls in any sane range. That byte is later read by `printFloat` as
the number of digits to print after the decimal point.

`printFloat` builds its output in a small, fixed-size buffer on the stack.
It writes one digit at a time for the integer part of the number, then pads
the remainder with `'0'` characters until it has written exactly
`decimal_places` digits — with no check that `decimal_places` actually fits
in the buffer it's writing into. Because the stored value can be any byte
(0–255), a `$<n>=<value>` command that sets it above what the buffer can
hold makes `printFloat` walk straight past the end of its local buffer,
overwriting the rest of its own stack frame — including its saved registers
and return address — with `'0'` bytes.

Any later call to `printFloat` (used throughout the firmware's status and
G-code reporting output to print coordinates, feed rates, and other
floating-point values) then triggers the overflow and hijacks the function's
return, since the return address itself has been overwritten with
attacker-chosen padding.
